\section{Introduction}
\label{sec:intro}

Computing a growth curve over the current human pangenome takes four hours and
$336$\,GB of RAM. The entire output is a few thousand integers. Throughout that
run, a $4.5$\,GB compressed copy of the same data sits on disk, unread, while the
tool rebuilds in memory the $369$\,GB text file it was compressed from
(Figure~\ref{fig:tax}).

This is the standard contract of compressed storage: space is saved now and paid
back when somebody uses the data. The payment is invisible while the expanded form
still fits in memory, which is why it is normally nobody's concern. It stops being
invisible when the expanded form no longer fits. Decompression is then not a
preamble to the computation but the dominant term, and the compressed archive is
treated as a shipping container, opened once and discarded, rather than as a
representation anything could execute on.

\input{fig_tax}

A pangenome graph stores the genomes of many individuals in one structure: nodes
are DNA segments, edges are admissible adjacencies, and each haplotype is an
orientation-signed walk through the
nodes~\cite{eizenga2020pangenome,liao2023draft}. Pangenomes are displacing the
single linear reference across human genomics because they remove reference
bias~\cite{lin2024measuring}, and they are exchanged as Graphical Fragment
Assembly (GFA) text~\cite{gfaspec}. The format scales badly in a specific way.
Topology grows sublinearly as haplotypes are added, since shared sequence
collapses onto shared nodes, but every haplotype's walk is written out
explicitly, so traversal records grow nearly linearly and come to exceed $90\%$ of
the file~\cite{heringer2025human}. Successive releases of the Human Pangenome
Reference Consortium graph show the trajectory: $48$\,GB, then $358$\,GB, then
$369$\,GB, with cohorts still an order of magnitude below where population studies
are heading~\cite{wang2022human}.

Those traversal records are also the most compressible part of the file, because
human haplotypes are nearly identical, and domain-specific compressors reduce that
$369$\,GB graph to roughly
$4.5$\,GB~\cite{siren2022gbz,heringer2025human,gfaz2026}. Storage is solved. Using
the data is not: every analysis begins by rebuilding something at least as large as
the GFA. \cmd{vg deconstruct} loads the graph and a snarl decomposition to emit
variants~\cite{garrison2018variation,hickey2020genotyping}, \cmd{odgi} builds a
succinct whole-graph index before any operation~\cite{guarracino2022odgi}, and
Panacus parses walk records into item tables~\cite{parmigiani2024panacus}. On the
two largest HPRC graphs, two of those three cannot load the input at all on a
$503$\,GiB machine.

The obvious escapes do not work, and Section~\ref{subsec:bg-alternatives} measures
why. Expanding once to fast local storage moves the cost rather than removing it,
because resident footprint, not read bandwidth, is what fails first. Buying memory
does not scale with a cohort still an order of magnitude from its target size.
Succinct whole-graph indexes~\cite{siren2022gbz} shrink the materialized object but
still materialize it, and they serve topology queries rather than the traversal
scans that dominate this workload.

The materialization is avoidable, for two reasons. First, the dominant component
of the file is already stored in a form that can be walked: a grammar-compressed
integer stream whose rule expansion is a local, bounded-depth array lookup, needing
no side table and no global state. Second, the analyses that consume pangenomes are
overwhelmingly \emph{path-centric folds}. They scan traversals in order and reduce
node visits into a small accumulator, a coverage histogram or an allele table, and
they neither mutate the graph nor need random node-to-step access. A fold does not
require its stream materialized; it requires the elements delivered in order, which
is exactly what such a column supplies.

\sys is an execution engine built on that observation. A query names the columns it
needs; \sys decompresses only the entropy-coded blocks backing those columns,
streams the still-grammar-compressed traversals through a visitor templated on the
query's fold so that decoding and reduction are one inlined loop, and merges
per-thread accumulators at the end. No list of path steps is materialized and no
whole-graph object is built, so resident memory is the compressed columns the query
touches plus the accumulator it chooses to keep, and nothing else.

This reverses the usual storage trade-off. Conventionally, a higher compression
ratio means a longer wait before computation starts, so ratio trades against access
latency. Here the compressed columns are what the inner loop walks, so a higher
ratio means fewer bytes touched per unit of biological work: on the $369$\,GB HPRC
graph, an $83\times$ reduction in bytes is what turns four hours into $41$ seconds.

We do not claim this for graph workloads in general. Operations needing arbitrary
node-to-step queries, graph editing, or topology rewriting belong to materialized
toolkits, and Section~\ref{sec:discussion} says so. We claim that a large and
growing class of pangenome analytics falls on the streaming side of that line, and
that for this class the compressed container is the right thing to compute on.

\paragraph{Relationship to prior work.}
The container format and its compressor are prior work, published
separately~\cite{gfaz2026}, and are \emph{not} a contribution of this paper. We
recap only the properties the engine depends on (Section~\ref{sec:container}) and
we do not re-evaluate compression ratio as a result. One exception is the
container's CPU compression and decompression backend, which we re-engineered and
report on here for the first time (Section~\ref{sec:container}); it is a
performance change to prior work rather than a contribution of this paper, and no
result in Section~\ref{sec:eval} depends on it.
Section~\ref{sec:principles} instead distills, from that format and from the
engine we built on it, the properties a compressed format must have for queries to
run on it at all, which is the part of this work we expect to transfer to other
domains.

\paragraph{Contributions.}
\begin{itemize}[noitemsep,topsep=3pt,leftmargin=*]
  \item \textbf{A characterization of computable compression.} Five properties
        (Section~\ref{sec:principles}) separating a compressed format a query
        engine can execute on from one that must be expanded first, with an
        account of where common storage formats sit against them.
  \item \textbf{A streaming execution engine over compressed traversals}
        (Section~\ref{sec:engine}): a decode primitive linear in emitted elements
        and free of side tables, a memory model bounding residency to the columns
        a query touches plus its accumulator, a bounded rule-leaf cache as the one
        explicit space--time dial, and a parallel schedule whose synchronization
        never touches the decode path.
  \item \textbf{Variant projection without a graph}
        (Section~\ref{sec:deconstruct}). Reference-relative variant calling is the
        most consequential pangenome derivation and the one least suited to
        streaming. We split it into an $O(V{+}E)$ topology-only site-discovery
        pass and a compressed-traversal allele fold, handle inversions in both,
        and reproduce the established tool's output at ${\sim}99.99\%$ position
        concordance with no materialized graph.
  \item \textbf{An evaluation of the storage argument, not only the speedup}
        (Section~\ref{sec:eval}): cold-cache end-to-end cost, a direct comparison
        against expanding to fast local storage first, the sensitivity of query
        time to compression ratio, and thread scaling. \sys is $15$--$613\times$
        faster than \cmd{vg deconstruct}, Panacus, and \cmd{odgi pav} at
        $3$--$25\times$ less memory, and answers questions on graphs they cannot
        load at all.
  \item \textbf{A negative result.} One of the six analyses builds an
        uncompressed join index, and it is that accumulator, not the traversal
        store, that exhausts memory at whole-genome scale. Computing over
        compression bounds the \emph{data} a query holds and says nothing about
        the state it chooses to build (Section~\ref{sec:discussion}).
\end{itemize}
